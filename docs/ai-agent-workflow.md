# AI 에이전트로 작업한 방식

이 저장소의 데모 재현, 3개 센터 규모 확장, 공개 준비는 AI 코딩 에이전트(Claude Code)에게 맡기고 진행했다.
여기서는 에이전트에게 무엇을 맡겼고, 무엇을 내가 직접 정했고, 어떻게 통제하고 검증했는지를 적는다.
사내 환경에서 쓴 프롬프트나 데이터는 넣지 않았다.

## 역할 나누기

내가 정한 것:

- 문제 정의와 목표 (예: README 데모를 VM에서 끝까지 재현, 서버 100대 이상의 다중 센터 구성)
- 안전 원칙 (아래 규칙들)
- 설계 갈림길에서의 선택 (네트워크 장비를 asset-sync로 넣을지 seed로 넣을지, 랙 위치를 자동 반영할지, NetBox를 초기화할지)
- 쓰기 작업 승인, root 권한 작업 실행, GitHub 공개 여부

에이전트에게 맡긴 것:

- 환경 점검, 명령 실행, 결과 수집과 비교
- 코드 구현과 테스트 작성, 데모 데이터 생성기 확장
- 문서 작성, 공개 전 비밀 정보 검사

## 처음에 준 규칙

작업을 시작할 때 다음을 지시문에 명시했다.

- 실제 회사 환경 버전 디렉터리는 읽지도, 복사하지도, 참고하지도 않는다. 이 저장소에 실제 IP, hostname, 시리얼이 들어오면 안 된다.
- sudo가 필요한 명령은 직접 실행하지 말고 목록만 보여 준 뒤 내가 실행했다고 할 때까지 기다린다.
- NetBox에 쓰는 단계는 무엇이 바뀌는지 먼저 보여 주고 승인을 받는다.
- 에러가 나면 원인을 확인하고 고친다. TLS 검증 끄기, 테스트 건너뛰기, 기대값을 결과에 맞춰 바꾸기는 하지 않는다.
- 단계마다 결과를 요약하고 다음으로 넘어가도 되는지 묻는다.
- 커밋은 해도 되지만 GitHub 저장소 생성과 push는 내가 확인한 뒤에 한다.

마지막 두 항목이 실제로 가장 많이 쓰였다. 에이전트는 단계가 끝날 때마다 표로 결과를 정리해 멈췄고, 나는 그걸 보고 다음 단계를 승인했다.

## 규칙을 파일로 고정

대화로만 규칙을 주면 다음 세션에서 사라진다. 그래서 저장소의 `CLAUDE.md`에 프로젝트 규칙을 적어 두고 에이전트가 매번 읽게 했다.

- NetBox 쓰기(`sync --apply`, bootstrap/seed의 `apply=true`, NetBox 배포)는 사용자가 이번 대화에서 승인했을 때만 한다. 이전 승인은 다음 작업으로 이어지지 않는다.
- 삭제 코드는 없고 추가하지도 않는다. 오래된 객체는 보고만 한다.
- `max_hosts`(기본 5)는 승인 없이 올리지 않는다.
- nmap, ping sweep, 포트 스캔 금지. 수집은 지정된 호스트만, 읽기 전용으로 한다.
- placeholder 값은 버리고, NIC 이름은 수집된 그대로 쓴다.
- NetBox에 값이 있고 다르면 덮어쓰지 않고 review로 보낸다.
- 토큰, 비밀번호, 시리얼은 대화나 커밋, 로그에 출력하지 않는다.

## 권한 구조

| 대상 | 에이전트 권한 |
|---|---|
| NetBox 조회 | 읽기 전용 토큰 (MCP, dry-run, 결과 검증) |
| NetBox 쓰기 | 쓰기 토큰은 `.env`에만 있고, 승인 게이트가 있는 명령(`make bootstrap-apply`, `seed-apply`, `demo-apply`)으로만 사용 |
| root 권한 작업 (Docker 설치, 방화벽) | 없음. 명령 목록만 만들고 실행은 내가 함 |
| NetBox 관리자 비밀번호 | 파일에만 저장. 에이전트에게 물었을 때도 값을 출력하지 않고 확인 방법만 안내함 |
| GitHub | SSH 키 생성과 push는 매번 확인 후에만 |

## 검증 방법

에이전트가 "완료했다"고 해도 그대로 믿지 않고, 미리 정한 기준과 맞춰 봤다.

- 단위 테스트: 매 변경 후 실행 (39개 → 44개)
- 기대 수치: README에 적힌 결과(자동 등록, 검토, 수집 실패, 제외 대수, 쓰기 건수)와 실제 실행 결과를 표로 비교
- 멱등성: 반영 직후 다시 실행해 쓰기 0건 확인
- 교차 확인: 실행 로그만 보지 않고 NetBox API를 읽기 전용 토큰으로 직접 조회해 객체 수를 셈
- 공개 전 검사: 추적 파일과 커밋 이력 전체에서 사설 IP, 토큰 패턴, 비밀번호, 실제 hostname, 커밋 작성자 정보 확인

## 에이전트가 틀렸거나 놓칠 뻔한 것

이 부분이 가장 쓸모 있었다. 검증을 넣어 둔 덕분에 모두 공개 전에 잡혔다.

**seed 장비 3대 누락.** 규모 확장 때 에이전트가 만든 데이터 생성기가 판교 서버홀 A와 B의 항온항습기 번호를 둘 다 01부터 매겼다.
`pg-crac-01~03`이 두 번 쓰이면서 216대 중 213대만 들어갔다. 반영 후 장비 수를 기대값과 비교하는 단계에서 바로 드러났다.
에이전트가 원인을 찾아 번호를 사이트 단위로 바꾸고, 생성기에 이름 중복 검사를 추가한 뒤 다시 반영했다.
다시 돌렸을 때 변경 0건인 것도 확인했다.

**테스트 데이터의 사설 IP.** 공개 전 검사에서 테스트 fixture에 `192.168.x.x`, `10.x.x.x` 주소가 두 개 나왔다.
문서용 대역(RFC 5737)으로 바꿨고, push 전이었으므로 커밋 이력도 다시 써서 첫 커밋부터 지웠다.

**커밋 작성자 정보.** 이력을 다시 쓰는 과정에서 VM에 git 사용자 설정이 없어 작성자가 `root@localhost.localdomain`으로 찍혔다.
push 전 작성자 확인에서 잡았고, 전역 설정은 건드리지 않고 해당 커밋만 바로잡았다.

**원격 저장소가 실제 환경 경로를 가리킴.** 저장소의 `origin`이 실제 환경 버전 디렉터리를 가리키고 있었다.
에이전트는 "읽지 말라"는 규칙에 따라 fetch나 push를 하지 않고 보고만 했다. 이후 내 지시로 원격을 지웠다.

**규칙 변경과 테스트.** 랙 위치를 자동으로 넣도록 sync 규칙을 바꾸자 "위치는 넣지 않는다"를 확인하던 기존 테스트가 실패했다.
여기서 기대값만 고쳐 통과시키면 "기대값을 결과에 맞추지 말라"는 규칙을 어기는 셈이다. 그래서 순서를 지켰다.
먼저 규칙 변경을 내가 승인했고, 그다음 테스트를 새 규칙에 맞게 바꿨다.
위치를 넣지 않아야 하는 경우(U 충돌, 기존 위치 있음, 장비 높이 불일치)를 확인하는 테스트 4개도 함께 추가했다.

## 설계 결정을 묻게 하기

큰 변경 전에는 에이전트가 먼저 선택지를 정리해 물어보게 했다. 규모 확장 때 물어본 항목은 이랬다.

- 네트워크 장비를 asset-sync가 엑셀로 등록할지, 별도 seed로 넣을지: 앞의 방식은 "검증 안 된 값은 쓰지 않는다"는 원칙과 충돌해서 seed를 골랐다.
- 랙 U 위치를 자동 반영할지: 시리얼 일치와 빈 U일 때만 반영하는 조건부 방식을 골랐다.
- 기존 NetBox 데이터를 지우고 다시 만들지: 가짜 데이터뿐이라 초기화를 골랐다.
- 규모: 서버 약 150대

각 항목에 추천안과 이유가 붙어 있어서 판단이 빨랐다.

## 아쉬운 점

- 규칙이 문장으로만 있다. 에이전트가 규칙을 어기려 해도 시스템이 막아 주지는 않는다.
  다음에는 Claude Code 권한 설정과 훅으로 `--apply`, `apply=true`, `down -v` 같은 명령을 실행 전에 막거나 확인받게 할 생각이다.
- 규모 확장 때는 초기화부터 반영까지 쓰기 단계를 한 번에 승인했다. "결과가 예상과 다르면 멈추고 보고한다"는 조건이었는데,
  seed 누락 때 에이전트는 멈추지 않고 원인을 고쳐 다시 반영한 뒤 마지막에 보고했다. 데모 데이터라 문제는 없었지만
  사내 환경이라면 단계별로 승인하고, 예상과 다를 때는 고치기 전에 반드시 멈추게 해야 한다.
- 효과를 숫자로 재지 않았다. 다음에는 작업 시간과 사람이 고친 횟수를 기록해 볼 생각이다.
